# z-report · 方案设计

> AI 驱动的拖拽式报表平台 —— 配置数据源之后，一句话让 AI 生成报表 / 视图 / 大屏
>
> 文档版本: v1.0 (2026-09-22)
> 状态: 方案已与产品负责人确认四项关键决策，待启动 M1 骨架搭建

## 一、产品定位

### 1.1 一句话描述

拖拖拽拽即可生成报表 / 视图 / 大屏（dataset 玩法），最终目标 **AI 驱动**：配置数据源之后，一句话就可以将报表产生出来。

### 1.2 核心产品概念

| 概念 | 说明 |
|---|---|
| **数据源 (DataSource)** | 独立板块。连接 + 凭证 + 元数据探测（库/表/字段），是所有数据的入口 |
| **ReportBook (报告簿)** | 某个领域相关的展示用视图的集合。book 内部树状组织（章节/页面），像一个应用一样可以**整体发布**被别人看 |
| **发布 (Publication)** | Book 的整体版本化快照，只读访问，改 Book 不影响已发布版本 |
| **内存 Join** | 数据来自多个数据源，数据源之间可以重新组织，支持在内存中将数据 join |

### 1.3 开发约束

- 技术底座使用 **z-boot 体系**（Spring Boot 2.7 + z-boot-dependencies BOM）
- 参考 z-lc 低代码平台（分层与 AI 集成模式）与 GitHub 同类开源产品
- **不在本地启动/构建后端**，部署由用户流水线处理
- **git 由用户自理**：助手不 commit、不 push，改动留在工作区

## 三、概念模型（六级模型）

Superset 的 Dataset 思想 + 自定义的 Book 思想：

```
DataSource 数据源板块        连接+凭证+探测（库/表/字段元数据）
    ↓ 引用
Dataset 数据集               语义层：物理表 / 自定义SQL / 多源join视图
                             + 计算字段(走 z-util-expr) + 字段级元数据(维度/度量/格式)
    ↓ 引用
Widget 图表                  绑定 Dataset 字段的聚合查询 + 图表类型 + echarts option
    ↓ 编排
View 视图页                  画布：拖拽布局 JSON + 筛选器联动
    ↓ 组织
ReportBook 报告簿            领域视图集合，树状目录（章节/页面），类"应用"
    ↓ 发布
Publication 发布快照         Book 整体版本化快照 → 只读访问（分享token / SSO）
```

**关键设计**：Book 整体发布 = 生成不可变快照（布局 JSON + 图表配置 + 数据集定义）。观看者只触达快照，修改 Book 不影响已发布版本——"像应用一样整体发给别人看"的实现方式，参考 z-lc 的 deployment 模式。

## 四、关键技术决策（已确认）

### 决策① 计算引擎：内建 typed 引擎 + z-util 全家桶深度复用

**背景**：z-util-math 的 DataFrame 核心存储是 `double[]`，join 为简化实现（按 index 连接）、merge 仅单键、无字符串维度列/日期类型/空值语义。BI 场景"维度"基本是字符串和日期，不能直接使用。

**结论**：z-report 内建类型化列式引擎，**不改造 z-util 本体**。

- 引擎定位：`z-report-dataset` 内部的 `Table`（typed 列：STRING/INT/FLOAT/DATE/BOOL + 空值位图）
- **API 形态对齐 pandas**（"内存级 join、很方便处理数据"的落点）：`join / groupby / query / assign / pivot` 一等公民
- 多键 hash join、groupby 聚合、表达式列原生支持
- 数值聚合函数复用 z-util-math；表达式求值复用 z-util-expr

z-util 复用矩阵：

| z-util 模块 | 在 z-report 中的角色 |
|---|---|
| z-util-math | pandas 风格 API 标杆 + 数值函数复用 |
| z-util-expr | 计算字段、过滤表达式求值 |
| z-util-workflow | 数据集转换 DAG 执行器（后期可可视化编排管道） |
| z-util-jdbc | MySQL 等库表数据源 + 连接管理 |
| z-util-parser | CSV/JSON 文件数据源接入 |
| z-util-http | HTTP/API 型数据源 |
| z-util-cache | 数据集结果两级缓存（元数据版本号失效） |
| z-util-office | 二期 Excel 导入导出 |

### 决策② LLM：内聚自研，留好切换缝

- 暂不依赖 z-agent-llm-gateway（当前在 z-opc/z-agent 仓，独立仓引用有工程边界问题）
- `z-report-ai` 内做 `LlmClient` SPI（OpenAI 兼容协议，配置 base-url/api-key/model 即可接 Qwen/GLM/DeepSeek 等）
- 所有 AI 能力只依赖该接口；后续 llm-gateway 剥离后，写一个 adapter 实现同一接口即可整体切换，业务代码零改动

### 决策③ 前端：schema 驱动的通用渲染器（低代码通用做法）

单一事实源是 **ViewSchema JSON**（页面布局 + widget 数组 + 每个 widget 的数据绑定/样式/交互）。三个生产者、一个消费者：

```
AI 一句话生成 ─┐
拖拽设计器编辑 ─┼──→ ViewSchema JSON ──→ UniversalRenderer 通用渲染器 ──→ echarts/antd
模板库 ────────┘                              (schema → echarts option 映射)
```

- 与 z-lc 的 viewconfig 思路同构
- 对 AI 最友好：AI 只产 JSON schema，生成/微调/diff 全是结构化操作
- 渲染永远走同一条路，"所见即所得"与"生成即可发布"天然成立

### 决策④ Maven 工程：独立自持

- `io.github.yuku123:z-report-*` + z-boot-dependencies BOM
- 不 parent 引 com.zifang:z-opc，保证**单独 clone 可编译**（避开 z-lc 的 parent 断链问题）

## 五、架构设计

### 5.1 模块划分

```
z-report/
├── z-report-common               # 领域模型/DTO/JSON Schema 定义(ViewSchema/WidgetSchema/DatasetSchema)
├── z-report-datasource           # 多数据源接入(基于 z-util-jdbc + z-boot-datasource-starter)
├── z-report-dataset              # ★核心：内存数据集引擎(typed Table/多源 join/聚合/表达式/DAG 管道)
├── z-report-render               # Widget 元数据 → echarts option 的服务端组装
├── z-report-book                 # Book 树/页面编排/发布快照/分享
├── z-report-ai                   # NL2Report：LlmClient SPI + 对话式生成
├── z-report-web                  # REST API 层
├── z-report-spring-boot-starter  # 可被其他 z-* 应用一行嵌入
└── z-report-bootstrap            # 启动器
```

### 5.2 数据流全景

```
DataSource(MySQL/HTTP/CSV)
   → Dataset 定义(物理表|SQL|多源join视图 + 计算字段)
   → z-util-workflow DAG: 下推SQL抽数 → 内存 Table 多键join → expr派生列 → groupby聚合
   → 小结果集(JSON)
   → Widget 绑定字段 → UniversalRenderer 渲染
   → View 页面 → Book 树状组织 → 整体发布快照(分享token/SSO) → 他人只读查看
```

策略：**下推与内存混合**——聚合/过滤能下推的转 SQL 在源库执行，跨源 join 与二次加工在内存 typed Table 完成；Dataset 结果用 z-util-cache 做两级缓存（元数据版本号失效）。

### 5.3 AI 链路（一句话生成）

两段式，产物全部为**结构化 JSON Schema**（可人工修正——与纯 NL2SQL 聊天产品的关键差异）：

1. **NL → 数据理解**：LLM 拿到"数据源 schema 摘要"上下文，生成 Dataset 定义（选表/join 键/维度度量）
2. **NL → 视图编排**：生成 Widget 数组 + 布局 JSON（ViewSchema），一步出 Book 初稿
3. **对话式微调**循环（"把柱状图换成饼图"、"按月份拆分"），复用 z-lc 的 MCP Tool 暴露模式（后续接入 z-agent 时启用）

AI 安全边界（原则）：AI 生成 SQL 只允许在只读账号 + 白名单 Dataset 上执行；AI 不直接触碰数据源凭证。

### 5.4 前端设计

- 技术栈：React 19 + Antd 6 + Vite + echarts-for-react（对齐 z-mist/z-gw/z-config 惯例）
- 核心组件：**UniversalRenderer**（消费 ViewSchema）、拖拽设计器（编辑 ViewSchema）、数据源/数据集管理面板、Book 树管理、发布分享页
- widget schema → echarts option 的映射收在渲染器内，新增图表类型 = 扩展一个映射器 + schema 枚举
